Lesson 01 of 05

What is a system?

Every product you use daily is not just an app — it is a system. This lesson teaches you how to see it that way.

Two ways to look at the same product

When you open an ATM, you see a machine that gives you cash. That is the user's view. When a developer looks at an ATM, they see something completely different.

🧑
User sees

Insert card → enter PIN → get cash. Simple.

⚙️
Developer sees

Card reader authenticates the user. PIN is verified against the bank's server. Balance is checked. Cash dispenser is triggered. Transaction is logged.

Same machine. Completely different mental model. A developer's job is to hold the second view in their head — always.

Every system has four layers

No matter which product you look at — a bank ATM, a food delivery app, a messaging tool — every system can be broken down into the same four things:

👤
Users

Who interacts with the system and what role does the system give them?

⚡
Actions

What can each user type actually do inside the system?

💾
Data

What information changes in the system when an action happens?

🔄
States

What different modes can the system be in at any moment?

Why does this matter? When a developer joins a company, no one sits them down and explains the whole product. They read code, explore the product, and build this mental model themselves. The faster they can do that — the better the developer they are. This week, you practice exactly that skill.
Lesson 02 of 05

Users & actions

Not everyone who uses a system has the same role. And not every role can do the same things.

Users are roles — not people

In system thinking, a "user" is not a human being — it is a role that the system recognises and gives specific permissions to. The same person can have different roles in different contexts.

Think of a library. A member can borrow books and return them. A librarian can add new books, remove damaged ones, and see everyone's borrowing history. Both are humans. But the system treats them completely differently.

The key test — Two people are different user types only if the system gives them different permissions. If they can do exactly the same things, they are technically the same user type — even if they behave differently.

A real example — an online library system

User typeWhat they can doWhat they cannot do
MemberSearch books, borrow a book, return a book, renew a loan, see own historyCannot add books, cannot see other members' history, cannot remove books
LibrarianEverything a member can do + add/remove books, view all borrowing history, send remindersCannot change system settings
AdminEverything a librarian can do + manage user accounts, configure the systemNo restrictions

Actions — be specific

Once you know your user types, list every action each type can take. Vague actions are useless. Specific actions are what developers actually build.

Too vague

"Uses the library system"
"Manages books"
"Does admin things"

Specific enough

"Borrows a book"
"Marks a book as damaged"
"Sends overdue reminder to member"

How to find actions — Imagine watching someone use the product for 10 minutes. Every distinct thing they tap, type, or trigger is an action. Write each one down separately.
Lesson 03 of 05

Data & states

Every action a user takes changes something in the system. And the system itself is always in one of several possible modes.

Data that changes — the "what changed?" question

For every action a user takes, ask yourself: what is different in the system one second after this happened? Something was created, updated, deleted, or read. That thing is the data that changed.

Let's use an online food ordering system at a college canteen as an example:

ActionData that changes
Student adds a meal to cartCart gains one item · item quantity in cart increases by 1
Student places the orderNew order record is created · cart becomes empty · canteen gets a notification · student's order history gains one entry
Canteen marks order as readyOrder status changes from "preparing" to "ready" · student gets a notification
Student cancels an orderOrder status changes to "cancelled" · payment refund is triggered · canteen's queue removes that order
Notice — one action (placing an order) changes multiple pieces of data at once. This is normal. The more things a single action changes, the more important — and risky — that action is.

States — what mode is the system in?

A system is never just "on." It exists in different states, and what a user can do often depends on which state the system is currently in. Think of a traffic light — it has only 3 states, but each one determines completely different behaviour.

States for a single order in the canteen system:

Cart (not placed) Order placed — waiting Being prepared Ready for pickup Picked up Cancelled
Ask yourself — can a student cancel an order that is already "ready for pickup"? Probably not. That means the "cancel" action depends on which state the order is in. States control which actions are possible. This connection is what makes system maps useful.
Lesson 04 of 05

Dependencies

In any system, some things cannot happen unless other things have already happened. These invisible chains are called dependencies.

What a dependency looks like

Think about an ATM. You cannot withdraw cash without first inserting your card. You cannot insert your card and go straight to withdrawal — you must enter your PIN first. Each step depends on the one before it.

Dependencies are not obvious until you look for them. But once you start seeing them, you see them everywhere.

The format — Write every dependency as: "X depends on Y because Z."

X = the action you want to take. Y = what must already exist or have happened. Z = the reason the system requires this.

ATM system — dependency examples

"Entering your PIN" depends on "card being inserted and recognised" because the system needs to know which account to verify the PIN against — without a card there is no account to check.
"Withdrawing cash" depends on "PIN being verified successfully" because the system will not allow any transaction until it confirms the person holding the card is the account owner.
"Printing a receipt" depends on "a transaction having been completed" because there is nothing to print until something has actually happened — the receipt is a record of an event, not a starting point.

Why dependencies matter

When a system breaks, it often breaks because a dependency was not respected. Something happened out of order. Or something that was supposed to exist did not exist yet.

Finding dependencies in a product is how a developer learns where the system is fragile — which parts can break and take many other parts down with them.

The question to ask — "What has to be true before a user can do this?" Every answer you find is a dependency. Keep asking it for each action on your map.
Lesson 05 of 05

Silent failures & the worked example

The most dangerous failure in any system is one the user never notices — until the consequences are already real.

Loud failure vs silent failure

A loud failure is easy to deal with. The page crashes. The error message appears. The user knows something went wrong and calls support.

A silent failure is different. The system appears to work. The user walks away thinking everything is fine. But underneath, something did not happen that should have.

Example — a library book return

A student returns a book at the self-checkout machine. The machine beeps, the screen says "Return successful." The student walks away. But the system failed to update the record. Three weeks later the student gets a fine for a book they already returned.

That is a silent failure. No crash. No error. Just a wrong outcome that shows up too late.

//Student books a cricket ground slot online
✓Booking form submitted
✓Confirmation screen shown: "Slot confirmed for 4pm"
✓SMS confirmation sent to student's phone
//Meanwhile, behind the scenes...
✗Database write timed out silently
✗Slot was never actually saved in the system
⚠Another student books the same slot — system allows it
⚠Both students arrive at 4pm. Only one can play.
✗First student had no idea anything went wrong until that moment.
Write silent failures from the user's perspective — not "the database threw a timeout exception." Instead: "The student arrives at the ground with their team, finds someone else already playing, and only then discovers their booking never existed in the system."

Google Meet — dependencies

"Share screen" depends on "Meeting active" because you cannot share before the meeting starts — there is no active session to share into.
"Who is speaking" is read simultaneously by the video layout, the participant list, and the live captions — it is the single most-read piece of data in the entire system.
If "Mute all" breaks, the host loses control of audio — but participants can still self-mute. The meeting does not collapse. It just gets noisier. Not every broken dependency crashes the whole system.

Google Meet — silent failure

If the "who is speaking" detection fails silently, the system highlights the wrong person's video as the main view. Every participant sees the wrong face enlarged on their screen. No error message appears anywhere. The meeting feels subtly wrong — conversations feel disconnected from the faces on screen — but nobody can name exactly why. The failure is invisible until someone points it out.
