Lesson 01 of 05

The tap to screen journey

Every time something appears on screen after you tap, a journey happened. This lesson teaches you what that journey looks like.

What you think happens vs what actually happens

When you tap a button on your phone and something appears, it feels instant. But between your finger lifting and the screen changing, a whole chain of events took place — across multiple machines, travelling hundreds of kilometres in milliseconds.

👆
What you see

Tap → result appears. Simple, instant, invisible.

⚙️
What actually happened

Your device sent a message. It travelled to a server. The server did work. It sent something back. Your device drew it on screen.

Understanding this journey is one of the most important mental models a developer can have. Every bug, every slowness, every broken page — comes from something going wrong in this journey.

A simple analogy — ordering at a restaurant

Think of a restaurant. You (the customer) ask a waiter for something. The waiter goes to the kitchen. The kitchen prepares it. The waiter brings it back. You receive it.

A web request works exactly the same way:

🧑
You

Your device. You make a request by tapping something.

🤵
The waiter

The internet. Carries your request to the right place.

👨‍🍳
The kitchen

The server. Does the actual work and prepares the response.

🍽️
The meal

The response. What comes back and gets drawn on your screen.

Video — Trace a request journey

Watch this short animation to see how a tap becomes a server request, how the server processes the like action, and how the response updates the screen.

The key insight — nothing appears on your screen that didn't first travel from a server. Every image, every piece of text, every number you see — came from somewhere. It was requested, prepared, and delivered. The screen is just the final drawing step.
Lesson 02 of 05

Requests & responses

Every conversation between your device and a server follows the same pattern — one side asks, the other answers.

The request — your device asking

When you tap something on a website or app, your device sends a message to a server. That message is called a request. A request says, in effect: "Give me this thing" or "Do this action."

Every request has three things:

📍
A destination

A URL — the address of the server and the specific thing being asked for.

❓
A method

What kind of request — GET (fetch something), POST (send something), PUT (update something).

📦
Sometimes a body

Extra information — like the username and password you typed into a login form.

The response — the server answering

After the server receives your request and does its work, it sends a response back. A response contains:

PartWhat it isExample
Status codeDid it work?200 = yes, 404 = not found, 500 = server error
HeadersMetadata about the responseWhat type of content it is, how long to cache it
BodyThe actual contentHTML, JSON data, an image, a file
Think of it like a letter — the envelope has the address and stamp (headers). The letter inside is the content (body). The postman confirms delivery (status code). Every response from every server follows this same structure.

One tap, many requests

Here is something that surprises most people: when you load a single page, your device does not send one request. It sends dozens. Sometimes hundreds.

The first request gets the HTML — the structure of the page. That HTML tells the browser: "now go fetch these images, this CSS, this JavaScript, this data." So the browser sends more requests. Each one comes back. The browser assembles them all into the page you see.

This is why pages load in stages — the text appears first, then images pop in, then the interactive parts start working. Each stage is a batch of requests completing. You are watching a waterfall of requests, not one single fetch.
Lesson 03 of 05

What the server does

The server is not a magic box. When a request arrives, it does specific, understandable work. This lesson teaches you to describe that work.

The server receives, looks up, and responds

When a request reaches a server, the server does three things in sequence: it receives the request and understands what is being asked, it does the work required to fulfil it, and it packages up the result and sends it back.

The "work" is the interesting part. Let's look at what different kinds of requests make the server do:

ActionWhat the server actually does
Opening a news articleFinds the article in the database by its ID, fetches the title, body text, author name, publish date, and related article IDs, packages them as JSON, sends back
Logging into a banking appReceives the username and password, looks up the username in the database, compares the password hash, if it matches creates a session token, sends the token back
Searching for a productReceives the search term, queries the database for products matching that term, sorts by relevance or price, paginates results, sends back a list
Submitting a contact formReceives name, email, message, validates they are not empty, stores in database, sends confirmation email, sends back a success response
Notice — in every case the server is doing something specific and describable. "The server processes the request" tells you nothing. "The server looks up the article by its ID and fetches its content from the database" tells you exactly what happened and where it could go wrong.

Lesson 04 of 05

The network tab

Every request your browser sends is visible. The network tab in DevTools lets you watch the entire journey happen in real time.

What is DevTools?

Every browser has a built-in set of developer tools. You open them by right-clicking anywhere on a page and selecting "Inspect." Inside is a tab called "Network" — and this tab shows you every single request your browser makes and every response it receives.

Think of it like an X-ray — the page looks normal to the user, but the network tab shows you the skeleton underneath — every request, every file fetched, every API call, every millisecond spent waiting for a server to respond.

Lesson 05 of 05

Silent failures in a journey

When something in the request-response journey goes wrong silently, the user experiences a consequence — but has no idea which step caused it.

The journey has many places to fail

Every step in a request journey is a potential failure point. The device might send a malformed request. The internet might be slow. The server might fetch stale data. The response might arrive incomplete. The browser might render something incorrectly.

Most of these failures show no error to the user. The page still loads. Something just looks or works slightly wrong.

Example — booking a movie ticket

✓User searches for shows — request sent to server
✓Server queries the database for available seats
⚠Database returns cached data from 10 minutes ago
✓Server sends back seat availability — looks correct
✓Browser draws the seat map — seats A1, A2 show as available
✓User selects A1 and A2 — taps "Book Now"
✗Server tries to book — A1 and A2 were sold 10 minutes ago
✗User gets "Booking failed" after filling in all details
✗User never knew the seat map was stale. They just feel frustrated.
The failure was in Step 2 — the server returned stale cached data. But the user experienced it at Step 6, after wasting time selecting seats and filling in details. The gap between where the failure happened and where the user felt it is what makes silent failures so damaging.

How silent failures in a journey connect to your system map

Last week you mapped a product as a system — you found users, actions, data, and states. This week's journey trace zooms into one of those actions. The data the server fetches in Step 3 of your trace is the same data you mapped last week.

When a step in the journey returns wrong data, it corrupts one or more pieces of your system map. The connection between the two exercises is real — a broken journey step is always a broken piece of data in the system.

You are ready. You now understand what happens between a tap and a screen update, what requests and responses are, what the server actually does, how to read the network tab, and how silent failures happen inside a request journey. Now go apply this to a real action in a product you know.
