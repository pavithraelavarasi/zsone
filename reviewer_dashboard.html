Week 01 · Phase 1 — Foundations

Map a Product You Love

Students pick one SaaS product they use daily and map it as a system — users, actions, data, states, dependencies, and silent failures. Submission is via SSH/SCP to a remote server.

⏱ ~5 hours🚫 No code📦 3 PDFs🖥 Terminal submission
📌
Context anchor
What students read first
▾
Every SaaS product — Instagram, YouTube, Zomato, Rapido — is a system. It has users who want things, actions they can take, data that changes when they act, and states the product can be in. When a developer joins a company, the first thing they must do is understand this system without being taught it from scratch. You will map a product you already understand as a user — which means you know more than you think.
🎯
The task — Parts A to D
Instagram · YouTube · Zomato · Rapido
▾
Part A
Write one paragraph: what does it do, who uses it, and what would happen if it went offline for a day?
Part B — Draw the system map
On paper (photograph it) or in a drawing tool, map every type of user, every action each type can take, every piece of data that changes when an action happens, and every state the product can be in. Connect them with arrows. There is no correct format — only more or less complete maps.
Part C — Find the dependencies
Identify and write 3 dependency statements in this exact format: "X depends on Y because Z."
Part D — The failure question
Pick the single most important action in your chosen product. If it fails silently — the user thinks it worked but it didn't — what is the worst case? Write 2 sentences from the user's perspective, not the engineer's.
📁

Core questions · ~15 min
▾
1
Point to one place on your map where data changes when a user takes an action. Walk me through exactly what changes and why.
Core
If stuck → "What is different in the system one second after a user does this?"
Good: Names specific action, data, causal connection.
Weak: "The database gets updated." No specific connection.
2
Read me your strongest dependency statement. Why does it exist — what would break for the user if it didn't?
Core
If mechanical → "If Y were removed entirely, what would the user see?"
Good: Names both parts and gives user consequence.
Weak: Restates X depends on Y without user consequence.
3
Your failure narrative — is the user aware something went wrong? Why is silent more dangerous than visible?
Core
If loud → "Can you describe a version where the user believes it worked?"
Good: Specific user, action, consequence without awareness.
Weak: "The page would crash." Loud failure.
4
How did you submit this assignment? Describe what you did in the terminal, step by step.
Core
Checking if they understood what they did — did they know they were on a remote machine?
Good: Explains connecting to server, seeing server's folders, exiting, then SCP from laptop.
Weak: Recites commands but cannot explain the two separate operations.
❓
Easy questions
▾
5
What is the meaning of the word Usecase? Can you list one usecase which is like an edge case for a User?
Easy
Good: Defines use case and describes a customer-focused edge case with specific user notification behaviour.
Weak: Vague definition or no specific user notification.
6
What is the meaning of the word State of an Application? How does it change when a user performs an action?
Easy
Good: Explains state as current data/view status and gives a before/after example.
Weak: Uses the word state without explaining how it changes.
7
What are the commands you used to connect to the remote host and copy the files inside it?
Easy
Good: Names SSH to connect and SCP to copy files.
Weak: Describes remote access without naming the commands.
✅
Accept / reject guide
▾
Accept when — Map has arrows. Dependencies have "because Z." Failure is from user's perspective. Files in correct server folders.
Send back when — Map has no arrows. No "because Z." Failure says "app crashes."
Week 02 · Phase 1 — Foundations

Trace a Request

Students zoom into one action from their Week 1 product and trace the full request-response journey. They observe it live in DevTools and identify a silent failure inside the journey.

⏱ ~5 hours🚫 No code📦 3 PDFs🌐 DevTools required
📌
Context anchor
▾
Last week you mapped a product as a system. This week you zoom in to a single moment — a user taps something, and something appears on screen. Between that tap and that result, a dozen things happen. After this week, you will know what they are.
🎯
The task — Parts A to D
Same product as Week 1
▾
Part A — Name the moment
Write one sentence: what is the action, and what appears on screen when it is done?
Part B — Trace the journey
Draw what happens — what the user does, what leaves the device, where it goes, what work happens there, what comes back, what appears on screen. Label each step with arrows.
Part C — Open the network tab and watch
Open DevTools → Network tab. Clear it. Perform the action. Write 5 observations: request count, first request, slowest request, one JSON/HTML response, and what caused any spinner or blank area.
Part D — The silent failure
Pick one step that fails silently. Write 2 sentences from the user's perspective. Connect it to your Week 1 map — which piece of data does this failure touch?
📁

▾

Easy questions
▾
1
What is meant by Client? Are you a client or is your device a client? What are all the clients that you know?
Easy
Good: Client is the requesting side, device runs the client, lists examples: browser, mobile app.
Weak: Says the user is the client or only gives one example.
2
Do you know what a port number is? What is the use of a port number in a system?
Easy
Good: Port identifies a specific service/process on a device so multiple services can run on the same machine.
Weak: Confuses port with IP address.
3
Can you explain the flow of a trace from beginning to end?
Easy
Good: Describes tap, request leaving device, server work, response returning, browser updating.
Weak: Only mentions request or response separately.
4
Show me where in the Network Tab you found how much time a request takes.
Easy
Good: Points to the Time column or waterfall bar.
Weak: Says network tab without identifying the timing indicator.
🟣
Hard questions
▾
1
What is a cookie? What are third-party cookies?
Hard
Good: Cookies store session/user info. Third-party cookies come from external domains for analytics/ads.
Weak: Calls cookies just a file.
2
You hit a request from Chrome to a server. Where in the request cycle is the browser info sent to the server?
Hard
Good: Browser info is sent in HTTP headers (User-Agent).
Weak: Says browser identity is part of the URL.
3
You have 2 requests where one request's input depends on the other's output. Do you make them parallel or sequential?
Hard
Good: Sequential — second request needs the first result before it can run.
Weak: Says parallel without accounting for the dependency.
Week 03 · Phase 1 — Foundations

Read the Web's Language

Students learn the developer words for the journey they traced in Week 2. They place 20 terms on their maps, translate between jargon and plain English, and identify gaps in their models.

⏱ ~4–5 hours🚫 No code📦 3 PDFs📚 20 glossary terms
📌
Context anchor
What students read first
▾
In 0.1 you mapped a product as a system. In 0.2 you traced the journey of a single request. You now have two maps and two weeks of thinking about how the web works — in your own words, without jargon.
This week, jargon arrives. Not because you need new concepts — because you need the words developers use for concepts you already understand. When a developer says "the client sends an HTTP request to the server, which queries the database, serializes the response as JSON, and the browser parses it and updates the DOM," they are describing exactly what you traced in 0.2. You just didn't have their words for it.
Jargon without experience is memorization. Jargon after experience is just naming what you already know.
📝
Part A — Place the terms
20 developer terms to place on your maps
▾
Below is a glossary of 20 developer terms. For each term:

1. Place it on your 0.1 map or your 0.2 trace — write which step, element, or part of your map it corresponds to
2. Write one sentence in plain English explaining what it means, using your own product as the example

If a term doesn't fit anywhere on your maps, say so and explain why. That is a valid answer.

Part B — Translate the developer conversation
▾
Read this paragraph written in full technical jargon:
"The client sends a GET request to /api/user/profile but the server returns a 404. Looks like the endpoint was renamed in last week's deploy and the client is still hitting the old URL. The DOM doesn't update because the fetch fails silently — the error handler just logs to console. The user sees their old cached profile data and thinks everything is fine."
Your job
1. Translate the entire paragraph into plain English — every technical term must be replaced with a concrete description of what is happening
2. Place the bug on your 0.2 trace — which step is failing?
3. Write a two-sentence failure narrative from the user's perspective — what do they experience, and what do they not know went wrong?
🔄
Part C — Go the other direction
▾
Take the silent failure you described in 0.2 Part D and rewrite it using as many terms from the glossary as are relevant.
Then show both versions side by side — your plain English version from 0.2 and your jargon version from this week. The meaning must be identical. Only the language changes.
🔍
Part D — Find the gaps in your maps
▾
Now that you have vocabulary, look back at your 0.1 map and 0.2 trace with fresh eyes.

1. Name one thing you now realise was missing from your 0.1 map. What term made you notice it?
2. Name one thing you now realise was missing from your 0.2 trace. What term made you notice it.

These gaps are not mistakes. They are evidence that your understanding grew. Naming them is more valuable than pretending your original maps were complete.
📁

Terms placed on maps without explaining the connection. Skipping Part D.

Core questions · ~20 min
Ask every student
▾
1
Pick any term from the glossary. Show me where it lives on your map or trace. Explain it in your own words using your product.
Core
If stuck → "Point to Step 4 of your trace. What's the developer word for what the server is doing there?"
Good: Names term, points to specific place, explains in product-specific language — "the server queries the database — in my product that means it's looking up which items are in my cart."
Weak: Recites a textbook definition without connecting to their product.
2
Read me your translation of the developer conversation. Now point to the step on your 0.2 trace where the bug is happening.
Core
If vague → "The server returned a 404. What does that mean happened?"
Good: Translates accurately and places failure on a specific step — "the request went out fine, reached the server, but the server couldn't find what was asked for because the address changed."
Weak: Translates word by word without understanding the chain of cause and effect.
3
Show me your Part C — the jargon version of your 0.2 failure. Read both versions. Is the meaning identical?
Core
If meaning drifted → "Point to the sentence that changed meaning. What did the jargon version add or lose?"
Good: Both versions say the same thing in different language, and student can identify any places where meaning accidentally changed.
Weak: Jargon version uses terms incorrectly or adds technical claims the student can't explain.
🔬
Deep questions
Strong submissions only
▾
4
You said a term doesn't fit on your maps. Why not? Is it because your maps are incomplete, or because the term describes something outside what you've mapped?
Deep
Good: Distinguishes between "my map is missing this" and "this term is about a different part of the system than I mapped." Both are valid and show different kinds of reasoning.
Weak: Cannot distinguish between the two reasons.
5
In Part D you named a gap in your 0.1 map. If you redrew it now with this vocabulary, what would you add?
Deep
Good: Names a specific addition — "I'd add state as a layer" or "I'd add the API as a boundary." Shows vocabulary changed how they see the system.
Weak: Says they would add more detail without saying what specifically.
🚀
Stretch
Exceptional students only
▾
6
A new developer joins your team. They've never seen your product. Using only the 20 glossary terms, describe your product's architecture in 60 seconds. Go.
Stretch
Listen for: fluency — can they assemble terms into a coherent description without stopping to recall definitions?
Good: Structures the description as a system — "client talks to server via API, server queries database, response renders in DOM."
Weak: Lists terms without connecting them into a system description.
✅
Accept / reject guide
▾
Accept when — Terms are placed on correct map or trace with product-specific explanation. Translation is accurate without meaning drift. Part D names specific gaps with the terms that revealed them.
Send back when — Textbook definitions with no product connection. Jargon version changes the meaning of the failure. Part D is skipped or says "everything was complete."
