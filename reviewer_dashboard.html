Week 01 · Phase 1 — Foundations

Map a Product You Love

Students pick one SaaS product they use daily and map it as a system — users, actions, data, states, dependencies, and silent failures. Submission is via SSH/SCP to a remote server.

⏱ ~5 hours 🚫 No code 📦 3 PDF deliverables 🖥 Terminal submission
📌
Context anchor
What students read first
▾
Every SaaS product — Instagram, YouTube, Zomato, Rapido — is a system. It has users who want things, actions they can take, data that changes when they act, and states the product can be in. When a developer joins a company, the first thing they must do is understand this system without being taught it from scratch. You will map a product you already understand as a user — which means you know more than you think.
🎯
The task — Parts A to D
Instagram · YouTube · Zomato · Rapido
▾
Part A
Write one paragraph: what does it do, who uses it, and what would happen if it went offline for a day?
Part B
Draw the system map

On paper (photograph it) or in a drawing tool, map:

• Every type of user
• Every action each type can take
• Every piece of data that changes when an action happens
• Every state the product can be in

Connect them with arrows. There is no correct format — only more or less complete maps.
Part C
Find the dependencies

Identify and write 3 dependency statements in this exact format:

"X depends on Y because Z."

Ask yourself: which action depends on another having happened first? Which piece of data is read by the most other parts? If one action were broken, which others would stop working?
Part D
The failure question

Pick the single most important action in your chosen product. If it fails silently — the user thinks it worked but it didn't — what is the worst case?

Write 2 sentences from the user's perspective, not the engineer's.
📁
Deliverables — 3 PDF files
Terminal submission only
▾
Compile your work into exactly 3 PDFs:
PDF 1
yourname_map.pdf — Your Part A, B, C and D answers
PDF 2
yourname_reflection.pdf — One page only: what surprised you most while mapping this product? What did you see as a developer that you never noticed as a user?
PDF 3
yourname_questions.pdf — Minimum 5 questions this assignment raised that you still cannot answer. These will drive next week's class.
Submission — Terminal only
You have 3 PDFs ready. Now figure out how to get them onto a remote server — without email, WhatsApp, or Google Drive.

You don't know how yet. That's the point.

Two things to discover on your own:
1. How do you get inside a remote machine from your terminal?
2. How do you send a file from your laptop to that remote machine?

Folder structure on the remote server:
• Inside the remote machine there is a folder named Document
• Inside Document → ZSOne/Tech/
• Create one folder named as your name inside Tech
• Place yourname_map.pdf inside your name's folder
• Place yourname_reflection.pdf inside the ZSOne folder
• Place yourname_questions.pdf inside your name's folder

Your submission is complete only when all 3 files are in the correct folders on the server.
If you get stuck:
Product feels too complex
Map only one feature area first. Is your product more complex than Google Meet? If yes, scope down before expanding.
Can't find dependencies
Pick any action on your map and ask: "What has to be true before a user can do this?" That answer is a dependency.
Can't find a silent failure
Ask: "What if this action appeared to succeed but the data didn't actually change?" Then describe what the user experiences next.
30 minutes stuck on terminal
Submit what you have with a specific note: "I completed Parts A–D but could not transfer files because [exact reason]." Specific and partial is always better than vague and complete.

How to use this — Core questions for every student. Deep if submission is strong. Stretch only for exceptional students.

Core questions
Ask every student · ~15 min
▾
1
Point to one place on your map where data changes when a user takes an action. Walk me through exactly what changes and why.
Core
If stuck → "What is different in the system one second after a user does this?"
Good: Names specific action, specific data, causal connection — "when a user adds to cart, cart_items gains one entry and stock count drops by one."
Weak: "The database gets updated." Generic, no specific connection.
2
Read me your strongest dependency statement. Why does that dependency exist — what would break for the user if it didn't?
Core
If mechanical → "If Y were removed entirely, what would the user see?"
Good: Names both parts and gives user consequence — "if login fails, the user can't add to cart because the cart is tied to their session."
Weak: Restates X depends on Y without explaining the user consequence.
3
Your failure narrative — is the user aware something went wrong? Why is a silent failure more dangerous than a visible error?
Core
If loud → "Can you describe a version where the user believes it worked?"
Good: Specific user, action, consequence without awareness — "buyer completes checkout, gets confirmation, order never processed, finds out only when order never arrives."
Weak: "The page would crash." That's a loud failure from the engineer's perspective.
4
How did you submit this assignment? Describe what you did in the terminal, step by step.
Core
Not checking syntax. Checking if they understood what they did — did they know they were on a remote machine?
Good: "I connected to a remote server, once inside I saw the server's folders not my laptop's, then I exited and used a different command from my laptop to send the files."
Weak: Can recite commands but cannot explain why two separate operations were needed.
🔬
Deep questions
Strong submissions only
▾
5
Which single piece of data in your map is read by the most other parts? What would happen if that data were wrong?
Deep
If stuck → "Imagine one row in a database got corrupted. Which row, if wrong, would affect the most things a user sees?"
Good: Identifies central data (user_id, session token) and chains consequences — "if user_id is wrong, the cart, order history, and notifications would all show wrong data."
Weak: Picks peripheral data with no downstream consequences.
6
If you joined this company as a developer tomorrow, what would you need to know that your map doesn't show?
Deep
If stuck → "What happens between when a user taps and when something appears on screen? What's missing?"
Good: Names server processing, data storage, concurrent users, error recording — things invisible in user-facing behaviour.
Weak: "I would need to learn the code." Too generic.
🚀
Stretch
Exceptional students only
▾
7
If this product had to handle 10x more users tomorrow — which part of your map would break first?
Stretch
Listen for: awareness that the most-read data is likely the bottleneck under load.
Good: Connects most-read data to load — "order status is read by user, driver, and restaurant simultaneously. Under 10x load that's the first thing that slows."
Weak: "The servers would crash." No system-level reasoning.
✅
Accept / reject guide
Submission quality
▾
Accept when — Map has arrows (not just a list). Dependencies have "because Z." Failure is written from user's perspective. Files in correct server folders.
Send back when — Map has no arrows. Dependency has no "because Z." Failure says "app crashes" — that's a loud failure.
Week 02 · Phase 1 — Foundations

Trace a Request

Students zoom into one action from their Week 1 product and trace the full request-response journey. They observe it live in DevTools and identify a silent failure inside the journey.

⏱ ~5 hours 🚫 No code 📦 3 PDF deliverables 🌐 DevTools required
📌
Context anchor
What students read first
▾
Last week you mapped a product as a system — users, actions, data, states. You saw it from above. This week you zoom in to a single moment: a user taps something, and something appears on screen.

Between the tap and the appearance, a dozen things happen. A message leaves the user's device. It travels to a machine somewhere. That machine does work. It sends a message back. The browser reads it and draws what you see.

Every web product you've ever used works this way. When it's fast, you don't notice. When it's slow, you notice but don't know why. After this week, you'll know why.
🎯
The task — Parts A to D
Uses the same product from Week 1
▾
Part A — Pick a moment
Choose one specific action in the product you mapped in Week 1. It must involve something visible changing on screen after you do it — loading a page, submitting a form, sending a message, adding an item to a cart, refreshing a feed.

Write one sentence: what is the action, and what appears on screen when it is done?
Part B — Trace the journey
On paper (photograph it) or in a drawing tool, draw what happens between the action and the result. Your trace must include:
• What the user does (the trigger)
• What leaves the user's device (the request)
• Where it goes (the server)
• What work happens there (what data is looked up, calculated, or changed)
• What comes back (the response)
• What the browser does with it (what appears on screen)

Label each step. Connect them with arrows showing direction — request goes out, response comes back. You won't get every detail right. That is fine. The point is to build a mental model of the journey, not a technically perfect diagram.
Part C — Open the network tab and watch
Open your product in a browser. Before you perform your action, open DevTools → right-click anywhere on the page → Inspect → Network tab. Clear the network log. Now perform the action and watch what appears.

Write five observations:
1. How many requests fired when you performed the action?
2. Pick the first request in the list. What URL did it go to? What did the server send back?
3. Pick the slowest request (sort by Time column). How long did it take? What was it fetching?
4. Find one request that returned HTML or JSON. Look at the Response tab. Can you connect what you see there to something visible on the page?
5. Was there a visible moment where you were waiting — a spinner, a blank area, a layout shift? Can you match that wait to a specific slow request in the network log?

If the action is too fast to observe, change the Network tab throttling dropdown from "No throttling" to "Slow 3G" and perform the action again.
Part D — Find the silent failure
Pick one step in your trace. Imagine it fails silently — it does not crash, does not show an error, but returns wrong data or takes too long.

Write two sentences from the user's perspective: what do they experience? What do they not know went wrong?

Then connect this to your Week 1 map — which part of your system map does this silent failure touch? Does it affect one piece of data or many?
📁
Deliverables — 3 PDF files
Terminal submission only
▾
PDF 1
yourname_trace.pdf — Parts A, B, C and D
PDF 2
yourname_reflection.pdf — One page: what surprised you when you opened the network tab? What did you expect to see versus what actually happened?
PDF 3
yourname_questions.pdf — Minimum 5 questions this assignment raised that you still cannot answer
Submission: Follow the same terminal process as Week 1. Place yourname_trace.pdf and yourname_questions.pdf in your name folder inside ZSOne/Tech/. Place yourname_reflection.pdf inside the ZSOne folder.
If you get stuck:
Can't figure out what happens between tap and page
Use the worked example as a template. Your product follows the same shape — request out, server works, response back, browser draws. The details differ, the shape doesn't.
Don't know what the server does
Describe it in plain English: "the server looks up the restaurant's menu." You don't need to know how. You need to know that it happens.
Network tab is overwhelming
Don't try to understand every line. Focus on the first request and the slowest request. Two requests understood well beats fifty glanced at.
30 minutes stuck
Submit what you have with a specific note explaining exactly where you got stuck.

Worked example given to students
Zomato restaurant page — full request traced
▾
Step 1
Tap registers. Browser reads the URL — the address of what to ask for.
Step 2
Browser sends a request: "Give me the page for this restaurant."
Step 3
Request travels through Wi-Fi, ISP, multiple hops to Zomato's server.
Step 4
Server looks up restaurant name, menu, ratings, images, delivery time estimate. Assembles and sends back.
Step 5
Browser reads HTML/CSS/data. Draws the page. Restaurant appears.
Silent failures shown — Slow hop at Step 3, stale location data at Step 4 (wrong delivery estimate), broken image URL at Step 5 (blank space, no error).
How to use this — Core for every student. Check whether they see the web as a journey with dependent steps — not a magic box.
🎯
Core questions
Ask every student · ~15 min
▾
1
Walk me through your trace. Point to each step. What is happening at each one?
Core
If stuck → "Start from the tap. What leaves the phone?"
Good: Names each step with product-specific detail — "my browser asks Notion's server for the page data, the server looks up which blocks are on that page, sends them back, and the browser draws each block."
Weak: "It sends a request and gets a response." No product-specific detail.
2
Point to the step where the server does its work. What data is it looking up or changing?
Core
If vague → "If you were the server and someone asked you for this page, what would you need to go find?"
Good: Names specific data — "it looks up my cart items, the prices, and whether each item is still in stock."
Weak: "It processes the data." No specifics.
3
Show me what you saw in the network tab. How many requests fired? Which one was the slowest?
Core
If stuck → "Open the network tab now. Perform the action. Point to the longest bar in the waterfall."
Good: Specific count, specific slow request connected to visible behaviour — "42 requests fired. The slowest was a 1.2s call to /api/feed — that's why the page shell appears first and the feed fills in after."
Weak: "There were a lot of requests." No specifics, no connection to what the user sees.
4
Your silent failure — is the user aware something went wrong?
Core
If loud → "That sounds like an error the user would see. Can you make it silent?"
Good: User experiences consequence without knowing the cause — "delivery estimate says 20 min but actually takes 50. The user doesn't know the server used stale location data."
Weak: "The page would crash." Loud failure, engineer's perspective.
🔬
Deep questions
Strong submissions only
▾
5
You said Step X depends on Step Y. What if Step Y is slow but not broken — takes 3 seconds instead of 0.3? What does the user experience?
Deep
Looking for: connection between delay and visible consequence.
Good: Names visible consequence — spinner, blank area, partial render — and what the user might do (wait, tap again, leave).
Weak: "It would be slow." No specific user behaviour described.
6
Look at your Week 1 map and your Week 2 trace side by side. Where does the trace touch the map? Which piece of data is the server looking up?
Deep
This tests whether they can connect both assignments as one continuous mental model.
Good: Connects both — "the cart data I mapped in Week 1 is what the server looks up in Step 4 of my trace."
Weak: Treats both assignments as separate, cannot find the connection.
🚀
Stretch
Exceptional students only
▾
7
If a thousand users all performed this action at the same second, which step in your trace would slow down first?
Stretch
Listen for: awareness that the server step is the bottleneck, that many users converge on one machine.
Good: Identifies server step as bottleneck — "the server is the single point where all requests arrive. The database query for everyone's feed would slow down first."
Weak: "The internet would be slow." No system-level reasoning.
✅
Accept / reject guide
Submission quality
▾
Accept when — Trace has labeled steps and directional arrows. Server step describes specific data looked up. Network tab observations have actual numbers and request names. Silent failure is from user's perspective. All files in correct server folders.
Send back when — "The server processes the request" — no specifics. Part C written without opening the network tab. Trace skips the return journey or is too vague.
