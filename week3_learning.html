Lesson 01 of 05

Jargon is just naming

You already understand how the web works. This week you just learn the words developers use for things you already know.

You already know this — you just don't have the words yet

Think about what you did in Week 2. You traced what happens when a user taps something — your device sent a message, it travelled to a server, the server did work, something came back, and the screen updated. You described all of that in plain English.

Developers describe the exact same thing — but with specific words. Those words are not harder concepts. They are just shorter, more precise labels for what you already traced.

The key idea — jargon without experience is memorisation. Jargon after experience is just naming what you already know. You have the experience. This week you get the names.

An example of what this looks like

Here is the same sentence written two ways:

Plain English (Week 2)

"Your browser sends a message to the server asking for the restaurant page. The server finds the restaurant's data and sends it back. The browser draws the page."

Developer language (Week 3)

"The client sends an HTTP GET request to the endpoint. The server queries the database and returns a JSON response. The browser parses it and renders the page."

Same sentence. Same meaning. Different language. By the end of this week you will be able to read the right side and understand it as naturally as the left side.

Why this matters

When you join a company as a developer, everyone around you speaks the jargon version. In code reviews, in meetings, in error logs, in documentation. If you only understand plain English but not the jargon, you are constantly translating — and translation takes mental energy away from actual thinking.

The goal is not to memorise definitions — it is to connect each term to a specific place on your Week 1 map or Week 2 trace. Once a term has a home on your mental model, you own it. It stops being vocabulary and starts being thinking.
Lesson 02 of 05

Architecture terms

These terms describe the structure of how a web product is organised — the players and their roles.

Click each term to reveal its plain English meaning

These are terms you already know from experience. The cards below show the jargon word — click to see what it really means in plain English.

clientArchitecture
You use this every day without knowing the name
The device or app that makes requests — your browser, your phone app. The client is always the one asking. It never has data of its own; it asks the server for everything it shows.
serverArchitecture
The machine that does the actual work
A computer running continuously somewhere that receives requests, does work, and sends responses. It holds the data. It processes the logic. The client just asks — the server actually does.
APIArchitecture
The agreed list of things you're allowed to ask the server
Application Programming Interface. The set of specific requests a client is allowed to make to a server. Think of it as a menu — you can only order what's on it. The server won't respond to requests not on the menu.
databaseStorage
Where the server stores everything permanently
The organised storage system where all the product's data lives — users, orders, messages, products. When the server "looks something up," it is querying the database. When data is saved, it is written to the database.

How these four connect

These four terms describe the skeleton of every web product. The client asks the server via the API, the server reads from and writes to the database, and sends back an answer.

TermRole in the systemPlain English example
clientThe askerYour phone running the food delivery app
serverThe workerThe computer at the food company that handles orders
APIThe agreed interfaceThe list of things the app is allowed to ask — "get menu", "place order", "track delivery"
databaseThe memoryWhere all the restaurant menus, user accounts, and order history are stored
On your maps — the client is your device in both Week 1 and Week 2 maps. The server is the machine you traced in Step 3 of Week 2. The API is the boundary between client and server — the list of things the server will respond to. The database is what the server reads from in Step 4 of your trace.
Lesson 03 of 05

Communication terms

These terms describe the messages that travel between client and server — what they are, what type they are, and what the reply looks like.

HTTP — the language of the web

Every message between a client and a server on the web uses HTTP — HyperText Transfer Protocol. Think of it as the agreed format for conversations. Like how a letter has a specific format (address, salutation, body, signature), every web message has a specific structure.

📤
HTTP request

A message from client to server. "I want this thing" or "do this action."

📥
HTTP response

The server's reply. Contains a status code, and usually some data or content.

🔢
Status code

A number in the response saying how it went. 200 = worked, 404 = not found, 500 = server error.

Request types — what kind of ask is it?

Not all requests are the same. HTTP has different "methods" — each one signals what the client wants to do:

GETFetch data
The most common request type
A request that asks for data without changing anything. Loading a page, viewing a profile, searching for a product — all GET requests. "Give me this information."
POSTSend data
Used when you submit something
A request that sends data to the server to create or change something. Submitting a form, placing an order, sending a message — all POST requests. "Here is data, do something with it."

URL and endpoint

Every request has a destination — a specific address on the server. That address is the endpoint. The full web address including the endpoint is the URL.

Example: In a library booking system, the URL might be:

https://library.example.com/api/books/search?q=history

The endpoint is /api/books/search — the specific address on the server that handles book searches. The full URL includes the domain and the endpoint together.

Status codes — what happened?

CodeMeaningPlain English
200OKIt worked. Here is your data.
404Not FoundThe thing you asked for doesn't exist at that address.
500Server ErrorSomething broke on the server's side. Not your fault.
301MovedThis address changed. Go here instead.
401UnauthorisedYou need to log in first.
Status codes matter for silent failures — a 404 that is not shown to the user is a silent failure. The request went out, the server said "not found," but the page shows the user their old cached data instead of telling them nothing loaded. This is exactly what happens in this week's developer conversation exercise.
Lesson 04 of 05

Data & display terms

These terms describe what the data looks like, how it is stored, and how the browser turns it into something visible.

How data travels and gets displayed

When a server sends data back to a client, it needs to be in a format both sides understand. And when the browser receives that data, it needs to turn it into a visible page. These terms describe those steps.

JSONData format
The universal language for data on the web
JavaScript Object Notation. The standard format for sending data between client and server. It looks like a structured list of labels and values — readable by humans and machines. When the server sends back a list of search results, it is almost always in JSON.
HTMLStructure
The skeleton of every web page
HyperText Markup Language. Describes the structure of a page — what elements exist, in what order, and how they relate. The browser reads HTML first to understand what the page contains.
CSSStyling
What makes a page look the way it looks
Cascading Style Sheets. Describes the visual appearance of a page — colors, fonts, spacing, layout. HTML says "there is a heading here." CSS says "that heading is dark blue, 24px, bold."
JavaScriptBehaviour
What makes a page do things
The programming language of the web browser. HTML is the structure, CSS is the appearance, JavaScript is the behaviour — what happens when you click, scroll, type, or when data arrives from the server.
DOMStructure
The browser's live model of the page
Document Object Model. When the browser reads HTML, it builds a live model of the page in memory — this is the DOM. When data arrives from the server and the page updates without reloading, JavaScript is updating the DOM.
renderDisplay
The act of drawing something on screen
To render is to take the instructions (HTML, CSS, data) and draw the visible result on screen. When developers say "the page renders," they mean the browser has finished drawing what the user sees.
parseProcessing
Reading and understanding a structured format
To parse is to read a structured format and extract meaning from it. The browser parses HTML to build the DOM. JavaScript parses JSON to extract data values. Parsing is always the step before doing something with the data.
stateData
The current condition of the system at any moment
State is the data that describes what the system looks like right now — who is logged in, what is in the cart, whether a request is loading. In Week 1 you called this "data that changes." State is the developer word for it.
cachePerformance
Saved copies that avoid repeat fetching
A stored copy of data or a page that can be reused without going back to the server. Caching makes things faster — but stale cache is a source of silent failures. If the cache has old data and the server is not asked again, the user sees something that is no longer correct.
Connect these to your maps — JSON is what travels in Step 4 of your Week 2 trace. HTML, CSS, and JavaScript are what the browser receives in Step 5. The DOM is what the browser builds in Step 5 before rendering the page. State is everything in your Week 1 data layer. Cache is the reason a silent failure can happen even when the server is working fine.
Lesson 05 of 05

Reading developer talk

Now that you have the terms, practice moving between developer language and plain English — in both directions.

Jargon → Plain English

Here is a developer sentence about a bug in a student attendance system. Click each highlighted term to see its plain English meaning.

The client sends a GET request to /api/attendance/today but the server returns a 500. The database query is timing out because the attendance table has too many rows. The DOM doesn't update — the cached data from yesterday still renders. The student sees yesterday's attendance and thinks today's has already been marked.
👆 The client — the student's browser or app. The device making the request.
📤 GET request — asking the server for data without changing anything. Just "give me today's attendance."
📍 /api/attendance/today — the specific endpoint (address) on the server that handles today's attendance data.
❌ Server returns a 500 — the server failed to complete the request. Something broke on the server's side.
🔍 Database query — the server searching through the stored attendance records. It took too long because there were too many records to search through.
🖥️ DOM doesn't update — the page does not visually change. The browser's live model of the page stays as it was.
💾 Cached data — a saved copy from a previous request. Because the new request failed, the browser shows this old copy instead of fetching fresh data.

Plain English → Jargon

Now go the other direction. Here is a plain English description of a bug in a hospital appointment system. Try to rewrite it using the developer terms you have learned.

Plain English version:

"A patient opens the app to check their appointment time. The app asks the server for the appointment details. The server looks it up in the system, but the record was moved to a different place last week, so the server says it can't find it. The app doesn't show an error — it just keeps showing the old appointment time the patient saw last week. The patient shows up at the wrong time."
What a developer version might look like:

"The client sends a GET request to /api/appointments/upcoming. The server returns a 404 because the endpoint was moved in last week's deploy. The error is not surfaced to the UI — the DOM continues to display cached state from the previous successful response. The patient sees stale appointment data and arrives at the wrong time."

The two versions say the same thing

Notice that nothing new was added in the jargon version. No new facts. No new concepts. Just more precise, shorter labels for the same events. That is the only difference between developer language and plain English — precision and brevity, not complexity.

The test for good jargon use — if you swap every technical term back to plain English, does the meaning stay identical? If yes, you used the terms correctly. If the meaning changed, you used a term incorrectly or added something the plain English version didn't say.
You are ready. You now know what each of the 20 developer terms means in plain English, where each one lives on your Week 1 and Week 2 maps, and how to move between jargon and plain language in both directions. Now apply these terms to your own maps.
