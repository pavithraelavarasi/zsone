Lesson 01 of 06

Jargon is just naming

You already understand how the web works. This week you learn the words developers use for things you already know.

You already know this — you just don't have the words yet

Think about what you did in Week 2. You traced what happens when a user taps something — your device sent a message, it travelled to a server, the server did work, something came back, and the screen updated. You described all of that in plain English.

Developers describe the exact same thing — but with specific words. Those words are not harder concepts. They are shorter, more precise labels for what you already traced.

The key idea — jargon without experience is memorisation. Jargon after experience is just naming what you already know. You have the experience. This week you get the names.

The same sentence — two ways

Plain English (Week 2)

"Your browser sends a message to the server asking for the restaurant page. The server finds the data and sends it back. The browser draws the page."

Developer language (Week 3)

"The client sends an HTTP GET request to the endpoint. The server queries the database and returns a JSON response. The browser parses it and renders the page."

Same sentence. Same meaning. Different language. By the end of this week you will read the right side as naturally as the left.

The goal — connect each term to a specific place on your Week 1 map or Week 2 trace. Once a term has a home on your mental model, you own it.

clientArchitecture
You use this every day without knowing the name
The device or app that makes requests — your browser, your phone app. Always the one asking. Never stores data itself; asks the server for everything it shows.
serverArchitecture
The machine doing the actual work
A computer running continuously that receives requests, does work, and sends responses. It holds the data. It processes the logic. The client asks — the server does.
APIArchitecture
The agreed list of things the server will respond to
Application Programming Interface. The set of specific requests a client is allowed to make. Think of it as a menu — you can only order what's on it.
databaseStorage
Where the server stores everything permanently
The organised storage where all the product's data lives — users, orders, messages. When the server "looks something up," it is querying the database.
On your maps — the client is your device in Week 1 and 2 maps. The server is the machine in Step 3 of your Week 2 trace. The API is the boundary between client and server. The database is what the server reads in Step 4.
Lesson 03 of 06

Communication terms

These terms describe the messages that travel between client and server.

HTTP — the language of the web

Every message between client and server uses HTTP — a standard format for conversations. Every web message has a specific structure: the destination, the type, the content, and the reply status.

📤
HTTP request

A message from client to server. "Give me this" or "do this."

📥
HTTP response

The server's reply. Contains a status code and usually data.

🔢
Status code

A number saying how it went. 200 = worked, 404 = not found, 500 = server error.

Request types

GETFetch
The most common request type
Asks for data without changing anything. Loading a page, viewing a profile, searching. "Give me this information."
POSTSend
Used when you submit something
Sends data to the server to create or change something. Submitting a form, placing an order, sending a message. "Here is data, do something with it."

URL and endpoint

Example: In a library system the URL might be:

https://library.example.com/api/books/search?q=history

The endpoint is /api/books/search — the specific address on the server that handles book searches.
Status codes and silent failures — a 404 that is not shown to the user is a silent failure. The request went out, the server said "not found," but the page shows old cached data instead of telling the user nothing loaded.
Lesson 04 of 06

Data & display terms

These terms describe what data looks like, how it travels, and how the browser turns it into something visible.

Click each term to reveal its meaning

JSONData
Universal web data format
JavaScript Object Notation. Standard format for sending data between client and server. Readable by humans and machines. Almost all API responses are JSON.
HTMLStructure
The skeleton of every web page
Describes the structure of a page — what elements exist and how they relate. The browser reads HTML first to understand what the page contains.
CSSStyling
What makes pages look the way they look
Describes the visual appearance — colors, fonts, spacing. HTML says "there is a heading." CSS says "that heading is dark blue, 24px, bold."
JavaScriptBehaviour
What makes pages do things
The programming language of the browser. HTML = structure, CSS = appearance, JavaScript = behaviour — what happens when you click, scroll, or when data arrives.
DOMStructure
The browser's live model of the page
Document Object Model. When the browser reads HTML it builds a live model in memory. When data arrives and the page updates without reloading, JavaScript is updating the DOM.
renderDisplay
Drawing something on screen
To take the instructions (HTML, CSS, data) and draw the visible result on screen. When the page renders, the browser has finished drawing what the user sees.
parseProcessing
Reading a structured format
To read a structured format and extract meaning. The browser parses HTML to build the DOM. JavaScript parses JSON to extract data values. Always the step before doing something with data.
stateData
Current condition of the system
State is the data that describes what the system looks like right now — who is logged in, what is in the cart. In Week 1 you called this "data that changes." State is the developer word.
cachePerformance
Saved copies that avoid repeat fetching
A stored copy of data that can be reused without going back to the server. Stale cache is a source of silent failures — if the cache has old data, the user sees something no longer correct.
Connect to your maps — JSON is what travels in Step 4 of your Week 2 trace. HTML, CSS, JavaScript are what the browser receives in Step 5. The DOM is what the browser builds before rendering. State is your Week 1 data layer. Cache is why a silent failure can happen even when the server is working fine.
Lesson 05 of 06

Reading developer talk

Practice moving between developer language and plain English — in both directions.

Jargon → Plain English

Here is a developer sentence about a bug in a student attendance system. Click each highlighted word to see its plain English meaning.

The client sends a GET request to /api/attendance/today but the server returns a 500. The database query is timing out because the attendance table has too many rows. The DOM doesn't update — the cached data from yesterday still renders. The student sees yesterday's attendance and thinks today's has already been marked.
👆 The client — the student's browser or app. The device making the request.
📤 GET request — asking the server for data without changing anything. Just "give me today's attendance."
📍 /api/attendance/today — the specific endpoint (address) on the server for today's attendance data.
❌ Server returns a 500 — the server failed. Something broke on the server's side.
🔍 Database query — the server searching through stored attendance records. It timed out because there were too many records.
🖥️ DOM doesn't update — the page does not visually change. The browser's live model stays as it was.
💾 Cached data — a saved copy from a previous request. Because the new request failed, the browser shows this old copy instead.

Plain English → Jargon

Now go the other direction. Read this plain English bug description and see how it looks in developer language.

Plain English — "A patient opens the app to check their appointment. The app asks the server for the details. The server looks it up but the record was moved last week so the server says it can't find it. The app doesn't show an error — it just keeps showing the old appointment time. The patient shows up at the wrong time."
Developer version — "The client sends a GET request to /api/appointments/upcoming. The server returns a 404 because the endpoint moved in last week's deploy. The error is not surfaced to the UI — the DOM continues to display cached state from the previous successful response. The patient sees stale appointment data and arrives at the wrong time."
The test — if you swap every technical term back to plain English, does the meaning stay identical? If yes, you used the terms correctly. If the meaning changed, you used a term incorrectly.
You are ready. You know all 20 terms, where they live on your maps, and how to move between jargon and plain English in both directions.
Lesson 06 of 06

Talk to servers from your terminal

Your browser is not the only thing that can make a request to a server. Developers do it directly from the terminal.

You have already done this — just differently

In Week 1 you used the terminal to connect to a remote server and move files. In Week 2 you watched your browser make requests in the network tab. This lesson connects both — using the terminal to make HTTP requests directly, with full visibility into what is sent and received.

The key idea — a browser and a terminal command both make HTTP requests. The difference is the browser renders the response visually. The terminal shows you the raw response as text — exactly what travels over the network before any rendering happens.

Before you send a request — is the server alive?

A developer never assumes a server is reachable. Before sending any request, they first check whether the server responds at all. Think of it like knocking on a door before trying to open it.

There is a terminal command designed exactly for this. It sends a small signal to a server address and tells you whether the server replied, how long it took, and whether any signals were lost on the way.

✅
Server responds

You get a reply for each signal. The server is alive and your network can reach it.

⏳
Request times out

No reply. The server is either down, unreachable, or blocking that type of signal.

❌
Cannot reach host

Your machine cannot even find the server's address. Could be DNS or no network.

What this tells a developer — if the server responds to the reachability check but your app fails, the problem is in your code. If the server does not respond at all, the problem is infrastructure. These two cases need completely different fixes.

Watch the terminal check

Making an HTTP request from the terminal

Once you know the server is alive, you can send it a real HTTP request. There is a terminal command that does exactly what your browser does — sends a GET request to a URL and shows you what the server sends back.

What comes back is the raw response — the same HTML, JSON, or data your browser receives before it parses and renders it. You are seeing Step 4 and 5 of your Week 2 trace happen directly in your terminal.

What the raw response looks like — if you request a webpage, you will see raw HTML — angle brackets, tags, attributes. It looks messy. That is because it is designed to be parsed by a browser, not read by a human. This is what your browser receives every single time you load a page.

Saving the response to a file

When the raw response scrolls past in your terminal, it disappears. The same command that makes the request has a way to redirect the output into a file instead of printing it. Once saved, you can open it in a text editor and read the raw response at your own pace — and connect what you see to the terms from Part A.

This connects to the terms you know — the file contains the HTTP response body. If the server returned HTML, that is the structure the browser will parse into the DOM. If JSON, that is the data the browser reads to update the page state.

Moving the file to the server

Once you have the response file on your laptop, move it to the remote server — exactly as you did in Week 1. Same SSH and SCP pattern. Same folder navigation. The only difference is what you are moving.

You are ready. You understand what a reachability check does, what a terminal HTTP request returns, how to save it to a file, and how to move that file to a server. Now research the specific commands, run them, and observe what happens.
